Code-review recurring-boundary addendum (GEPA round 3)

This short addendum covers only confusions recurring across two independent
train-only prompt rounds. Match the human's requested change and primary stated
consequence, not a topical mechanism mentioned along the way.

- Keeping incidental files/date-only changes out of a PR so the change remains
  focused and reviewable is a54, not version-control literacy a126. Use a126
  for traceability or correct commits, branches, and merges themselves.
- Avoiding widespread call-site edits or localizing future change is a17.
  Use a62 only when limiting collaborator knowledge/reach-through is itself the
  criterion.
- A direct Boolean/expression rewrite for clarity is a22. Use a1 for unused
  elements or broader needless design/complexity.
- Which inputs/values/returns an API admits and its simple usage path is a11.
  An exported constructor/type mismatch or the public surface itself is a44.
- Keeping implementation state local/hidden is a35. Package/module/class-tree
  organization and access-boundary layout is a92.
- A named linter, analyzer, auto-fixer, or automated CI rule is a42. Mere
  compliance with a project standard, without automated enforcement, is a110.

a10 and a39 are overlapping test-design leaves. If the quote only asks for
visible table-test data or generic maintainability and both cards remain
plausible, return MATCH_FAMILY_ONLY; do not guess an exact leaf.
