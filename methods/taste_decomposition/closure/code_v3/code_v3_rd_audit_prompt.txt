You are auditing a pool of scoring criteria that were written by other
models. Your job is a ROUTING decision, made blind: you are NOT told who wrote each
criterion or what it was written for.

For each criterion, decide:

  "quality_relevant" -- the criterion measures a property that a careful maintainer
      would count as genuine evidence about how good the pull request is as a contribution to that repository. It is about the substance of
      the change, the engineering judgement it shows, the correctness and design of
      the code, the testing, or what the author actually tells a reviewer.

  "incidental" -- the criterion measures something that may well PREDICT how the item
      fares but is not itself how good the pull request is as a contribution to that repository: length or verbosity, formatting and layout
      habits, template scaffolding, checklists, conventional-commit prefixes and issue
      references, boilerplate or bot-generated phrasing, project- or ecosystem-specific
      style markers, subject-matter or language markers, temporal tells, or a textual
      fingerprint of some upstream circumstance of the change's production (who wrote
      it, how familiar they are with the maintainers, what tooling produced it, where
      it falls in the repository's history).

The corpus is: pull requests submitted to open-source GitHub repositories, each shown as its title, its description, the inline review comments left on it, and its code diff. Each item is a pull request.

SECOND JUDGEMENT, only for criteria you label "incidental". Some incidental channels have
an upstream cause that plausibly ALSO produces genuinely better work (for example, a
long-standing contributor may both be treated more favourably AND actually write better
patches). Return `mixed`: true when you think the upstream cause plausibly produces real
how good the pull request is as a contribution to that repository too, false when the channel looks like pure nuisance. For criteria you label
"quality_relevant", return mixed=false.

Judge each criterion ON ITS OWN TEXT. Do not try to guess which pool it came from, and
do not let the ORDER of the list influence you.

CRITERIA:

[X01] Complexity-Discussion Surface Extent
Give 10 when the pull request contains extensive visible discussion of design, alternatives, tradeoffs, architecture, performance, or complexity across its title, description, and comments. Give 0 when such discussion is absent or minimal. Count or estimate the amount and prominence of this discussion only; do not judge whether it is insightful, accurate, or beneficial.

[X02] Concurrent-Activity Cue Extent
Give 10 when the pull-request text contains many cues of surrounding activity, such as parallel changes, conflicts, release trains, backports, active migrations, deadlines, or coordination with other work. Give 0 when none of these cues appear. Measure textual evidence of concurrent repository activity only; do not judge urgency, organization, or contribution quality.

[X03] Requirement-Bounded Design Simplicity
Give 10 when the implementation uses only mechanisms needed for the evidenced requirements, keeps boundaries and control flow understandable, and avoids speculative abstractions, unnecessary options, premature optimization, and incidental complexity. Give 0 when the design is materially over-engineered, speculative, or harder to reason about than necessary, regardless of explanatory prose. Judge the code and substantive design only; do not reward comment length, description length, or review-comment volume.

[X04] Semantically Useful Documentation
Give 10 when documentation accurately explains behavior, constraints, rationale, or usage, is sufficient for a reader to act correctly, and has examples or comments that match the implementation. Give 0 when documentation is absent, misleading, purely decorative, or merely restates code without useful meaning. Judge communicative substance only; do not reward headers, lists, fences, fragments, doc-comment syntax, or document length.

[X05] Names the concrete failure or limitation it addresses
Score 0-10 for whether the pull request identifies a specific, concrete failure, limitation or behaviour that the change addresses -- a particular error, a case that breaks, a measured shortcoming -- rather than a generic aim. 10 = one specific failure or limitation is named precisely enough to be reproduced or checked; 0 = only generic aims ('improve', 'clean up', 'refactor') with nothing specific. Judge the specificity of the substance, not the length of the text.

[X06] Substantive Behavior-Preserving Refactoring
Give 10 when the change materially improves structure or removes an identifiable design smell, preserves intended behavior, uses appropriate refactoring boundaries, and provides code or validation evidence that risk is controlled. Give 0 when the change is cosmetic-only, introduces behavioral uncertainty, lacks a meaningful structural rationale, or leaves avoidable risk. Judge refactoring substance only; do not reward addition/deletion ratio, title wording, headings, or comment length.

[X07] Evidence of Correct, Complete Contribution
Give 10 when the diff and plain-language explanation show that evidenced requirements are implemented, appropriate validation is present, behavior is coherent, and avoidable technical debt is not introduced. Give 0 when correctness, completeness, validation, or debt concerns remain, even if the description is long and impeccably templated. Judge substance only; do not reward headings, checklists, issue links, title conventions, description length, or template completion.

[X08] States why the change is needed
Score 0-10 for whether the pull request says WHY the change is needed -- the problem, need or goal that motivates it -- as opposed to only describing what was changed. 10 = the motivating problem or goal is stated explicitly and specifically enough that a reader who did not know about it would understand it; 0 = the text restates the diff, or says nothing about motivation at all. Judge whether the reason is actually given, not how tidily the text is laid out and not how long it is.

[X09] Conventionlessness Cue Extent
Give 10 when the pull-request text contains many explicit cues that the surrounding codebase lacks settled idioms, such as establishing a first pattern, choosing among competing conventions, or describing ad hoc structure. Give 0 when no such cues appear. Measure cue extent only; do not judge the contribution or whether conventionlessness is good or bad.

[X10] Version-Era Anchor Extent
Give 10 when the pull request contains many concrete temporal anchors, including language, runtime, dependency, tooling, platform, deprecation, or migration versions that locate the work in the repository’s lifecycle. Give 0 when no such anchors are visible. Measure anchoring detail only; do not judge whether the versions or migration choices are appropriate.

[X11] Communication-Scaffolding Extent
Give 10 when the pull request visibly contains extensive communication scaffolding, such as long descriptions, multiple sections, many bullets, issue references, conventional title or message patterns, and other structured metadata. Give 0 when it is brief and largely unstructured with few or no such markers. Count or estimate visible form only; do not judge whether the communication is clear, sufficient, accurate, or useful.

[X12] Submission-Norm Marker Extent
Give 10 when the pull request visibly contains many submission-hygiene markers, such as template sections, checklist items, structured headings, issue references, conventional title wording, and explicit status or test sections. Give 0 when these markers are absent. Count or estimate their presence and prominence only; do not decide whether they are useful, correct, or desirable.

[X13] Documentation-Format Marker Extent
Give 10 when the text visibly contains many formatting conventions, including headers, bulleted or numbered lists, structured steps, fenced multi-line code, concise summary fragments, and language-specific documentation-comment forms. Give 0 when these markers are absent or minimal. Count or estimate convention presence only; do not decide whether the formatting is appropriate, consistent, readable, or valuable.

[X14] Actionable Change Rationale
Give 10 when the title and accompanying text accurately explain what changed, why it was needed, relevant constraints, expected effects, and review-relevant risks at a detail level proportionate to the change, without merely narrating the diff. Give 0 when context and rationale are missing, generic, misleading, or replaced by diff narration, even when the submission is lengthy and highly structured. Judge informational substance only; do not reward bullets, headings, issue references, templates, or word count.

[X15] Conventional-commit and issue-reference formatting
Score 0-10 for how much conventional formatting furniture the title and description carry -- a conventional-commit prefix such as 'feat:', 'fix:', 'chore(scope):', a bracketed ticket tag, and '#1234' / 'Fixes #1234' issue references. 10 = a conventional prefix and one or more issue references are present; 0 = a plain title with no prefix and no issue reference anywhere. Count the formatting conventions only; this is not a judgement of whether the change or its description is good.

[X16] Extent to which a pull-request template is filled in
Score 0-10 for how much of a repository pull-request template is visibly present and populated -- headed sections such as 'Description', 'Motivation', 'Type of change', 'How Has This Been Tested?', 'Checklist', ticked or unticked checkbox lists, and similar scaffolding. 10 = a full template with most sections and checkboxes present; 0 = free prose or nothing, with no template scaffolding at all. Count the scaffolding only; do not judge whether what is written in it is any good.

[X17] Automation-Generated Submission Extent
Give 10 when the text strongly exhibits machine-generated submission signals, such as bot authorship, standardized dependency-update wording, generated changelog language, repetitive metadata, or formulaic update descriptions. Give 0 when no such signals are visible and the text appears individually authored. Measure automation-signature extent only; do not judge the contribution or the automation.

[X18] Shared-History Presupposition Extent
Give 10 when the text heavily presupposes shared project history through references to longstanding components, prior migrations, recurring maintainer practices, internal shorthand, or ongoing conventions. Give 0 when the pull request is self-contained and contains no such presuppositions. Measure reliance on shared history only; do not judge whether that reliance improves communication or contribution quality.

[X19] Refactor-Presentation Marker Extent
Give 10 when the pull request visibly uses many refactor labels, summary annotations, before-and-after descriptions, structured refactor sections, explanatory comments, or separated structural change regions in the diff. Give 0 when these presentation markers are absent or minimal. Count or estimate visible packaging only; do not judge its clarity, value, or the refactor itself.
